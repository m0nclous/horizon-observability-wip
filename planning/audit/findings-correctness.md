# Correctness bugs (C1-C26) with adversarial verdicts

Audit of the legacy pilot (now in `legacy/`), 2026-10-16. File:line references point to the legacy layout (`src/...` = `legacy/src/...`).

## Summary

I read the full runtime code: the subscriber, storage (with its Lua), the state reader (with its Lua), all the collectors, repositories, HTTP layer, console command and job. I checked the behaviour against the installed vendor sources (laravel/framework 12.70, horizon 5.50.1, spatie/laravel-prometheus 1.4.0, promphp 2.15.1, predis 2.4.1, phpredis 5.3.7) and confirmed the most important findings with probes against a scratch Redis 7 under testbench. Four high-severity issues are confirmed by probes:
- **No job_batches table:** `/metrics` returns 500 on every scrape. QueueBatchesCollector indexes the `[]` that ScrapeCache returns after a failure.
- **predis:** every attempt with a duration fails to record (`TypeError`), because the pipelined EVAL uses phpredis argument order. Nothing is written and a warning is logged per job.
- **Persistent spatie cache:** the counters inflate on every scrape (10 → 20 → 30), because absolute values are published through `inc()`.
- **Job-list endpoints:** they are open to any IP by default and expose exception messages. They also run unthrottled 10k-row Redis scans.

Medium issues:
- Collector failure isolation is incomplete.
- Sync jobs are now recorded, because Laravel ≥ 12.4x fires JobAttempted in SyncQueue.
- Every app replica exports the same global counters, so they are multiplied by the replica count.
- The oldest-job age includes the dispatch delay and earlier attempts, which triggers false long-wait alerts.
- `job_class` and batch labels can grow without bound, and stale series are never pruned.
- Redis Cluster does not work at all.
- Workers stall when the metrics Redis is unreachable.
- Each scrape runs heavy Lua over full payloads.
- The JSON endpoints use too much memory and scan everything even when a filter matches nothing.
- The supervisor filter breaks for supervisors with `balance=false`.
- The batches query loads all never-finished batches on every scrape.
- When the package provider registers before Horizon's and `config/horizon.php` is not published, Horizon loses its `web` middleware.

The low-severity items cover redundant `ready_at` keys, retry and timeout races, the counter wipe on first scrape, clock-skew effects, a full `app/` scan per scrape under PHP-FPM, metric-name collisions with spatie, hardcoded office/Russian strings, offset pagination over live sorted sets, and the load-test command being shipped as runtime code.


## C1 [high] QueueBatchesCollector turns any batch-source failure into a /metrics 500 (no job_batches table, DynamoDB batching, DB hiccup)

**Verifier verdict: confirmed.** ScrapeCache::remember returns [] on any Throwable (ScrapeCache.php:42). perKind/perBatch then index ['kinds']/['batches'] with no fallback (QueueBatchesCollector.php:178,198). Laravel's HandleExceptions turns the 'Undefined array key' warning into an ErrorException. spatie's RenderCollectorsAction calls each gauge's value closure with no try/catch (checked in vendor spatie 1.7.1), so the whole /prometheus response becomes a 500. One correction: Laravel 11+ skeletons create job_batches by default, so 'very common' is overstated. Still reachable on any DB error, on older apps without the table, or with DynamoDB batching.

- **Location:** src/Prometheus/QueueBatchesCollector.php:178, src/Prometheus/QueueBatchesCollector.php:198, src/Prometheus/QueueBatchesCollector.php:226-242, src/Prometheus/ScrapeCache.php:42
- **Detail:** stats() runs inside ScrapeCache::remember(). If the closure throws, remember() returns []. perKind() then reads `$this->stats()['kinds']` and perBatch() reads `$this->stats()['batches']` with no fallback. Laravel turns the resulting 'Undefined array key' warning into an ErrorException, and the spatie renderer aborts the whole response. The probe ran with Redis up and no `job_batches` table (very common, since batching is optional). Seven gauges threw `ErrorException: Undefined array key "kinds"/"batches"` and GET /prometheus returned 500 on every scrape. The same happens when `queue.batching.driver` is dynamodb (the query hits the default DB connection) or on any transient DB error. Because /metrics is shared with all the app's other metrics, they all disappear. This is despite the provider docblock (HorizonPrometheusGrafanaServiceProvider.php:30) promising that package collectors never break /metrics.
- **Recommendation:** Make the cache return a typed default per source: `remember($source, $read, default: ['kinds' => [], 'batches' => []])`, or use `?? []` at the call sites. Skip the collector entirely when `queue.batching.driver` is not database, or when the table does not exist (check once per process). Add a test that renders /metrics with each source throwing.

## C2 [high] With predis, recordAttempt() throws a TypeError and records nothing

**Verifier verdict: confirmed.** Reproduced against vendor predis 2.4.1. With a key prefix (Laravel's default config sets one), KeyPrefixProcessor::evalKeys runs `$arguments[1] + 2` on the array argument and throws `TypeError: Unsupported operand types: array + int` while the pipeline is still being built, so KEYS * stayed empty. Without a prefix the array argument causes an 'Array to string conversion' warning (an ErrorException under Laravel) and a server error. Laravel's PredisConnection has no pipeline() override, so `$pipe` really is a raw Predis pipeline. The predis branch at QueueJobMetricsStorage.php:437 shows predis is meant to be supported.

- **Location:** src/QueueJobMetricsStorage.php:106-132 (eval at 120-126)
- **Detail:** Inside the pipeline callback `$pipe` is the raw client. The call uses the phpredis signature `eval(script, array $args, int $numKeys)`. Under predis `$pipe` is `Predis\Pipeline\Pipeline`, whose EVAL expects `(script, numkeys, ...args)`. Probe: `recordAttempt(..., durationSeconds: 0.3, ...)` with `database.redis.client=predis` threw `TypeError: Unsupported operand types: array + int` while the pipeline was still being built. Because of that no command was sent: jobs_total, buckets, sums and extremes were all missing (KEYS * was empty). Every job with a measured duration (nearly all of them) is lost, and finish() logs a warning per job. The code clearly intends to support predis (see the comment at :437 and HorizonJobsRepository's predis handling), but this path was never exercised. resetCountersAfterRedisRestart() works only because it goes through Laravel's normalized `Connection::eval`.
- **Recommendation:** Do not call eval on the raw pipeline object. Either run the extremes script outside the pipeline through `$this->redis()->eval($script, 2, ...)`, which Laravel normalizes for both clients, or branch on the client class. Better still, fold the whole attempt into one Lua script called through `Connection::eval`. Add a CI matrix over phpredis and predis.

## C3 [high] Counters are published as absolute values through inc(), so they inflate on every scrape with any persistent spatie cache

**Verifier verdict: confirmed.** Checked in vendor spatie 1.7.1: `prometheus.cache` set to a store name switches the scoped CollectorRegistry to LaravelCacheAdapter, which persists across requests. Counter::handleValueAndLabels then calls incBy(absolute value) on every render, so values inflate on each scrape. Gauge series that disappear also stay in the cache. The only mitigations are the README and the config comment; nothing in code checks `prometheus.cache` or `wipe_storage_after_rendering`. The spatie config comment advertises the cache for keeping metrics between requests, so this misconfiguration is realistic.

- **Location:** src/Prometheus/QueueJobsCollector.php:31-35, src/Prometheus/QueueJobsCollector.php:72-93
- **Detail:** Absolute Redis totals are pushed into promphp counters with `incBy`. This is only correct while spatie builds a fresh InMemory registry per request (`prometheus.cache = null`). The probe set `prometheus.cache = 'file'`, recorded 10 attempts and scraped three times. Result: `queue_jobs_total{status="completed"}` read 10, then 20, then 30, and `_bucket/_sum/_count` grew the same way. A persistent cache is exactly the setting spatie documents for apps that keep their own counters between requests, so many installs will have it. Under it the gauges also go stale: `queue_jobs_pending` for a class that is no longer pending keeps its last value forever, because only current classes are set. The README asks for `'cache' => null`, but nothing in code checks it, and the result is silently wrong rates on the dashboard and in the failure-rate alert.
- **Recommendation:** Do not write absolute values through spatie's counter API. Render the package's families directly, either with a custom MetricType/Collector that writes samples into a throwaway InMemory registry, or as a separate spatie urlName served by its own action. At minimum, refuse to register these collectors and log an error when `config('prometheus.cache') !== null`. Test this.

## C4 [high] Job-list JSON endpoints are open by default, leak exception text and allow cheap Redis DoS

**Verifier verdict: confirmed.** Vendor AllowIps returns $next() when allowed_ips is empty, and spatie's default allowed_ips is []. registerRoutes() (provider:92-102) runs unconditionally, ignoring both `prometheus.enabled` and HPG_ENABLED. failed-jobs returns up to 1000 bytes of each exception's first line (HorizonJobsRepository EXCEPTION_MAX_BYTES). The scan is up to SCAN_LIMIT/CHUNK = 20 ZRANGEBYSCORE calls plus 10k HMGETs per request, with no auth and no throttle. The README warns about this (README:111-116), but the shipped default is open.

- **Location:** config/horizon-prometheus-grafana.php:38-41, src/HorizonPrometheusGrafanaServiceProvider.php:92-102, src/Http/Requests/GetHorizonJobsRequest.php:69-83, src/HorizonJobs/HorizonJobsService.php:50-54
- **Detail:** The default middleware is spatie's AllowIps, which lets every IP through when `prometheus.allowed_ips` is empty (spatie's default). Probe: GET /metrics/horizon/failed-jobs and /pending-jobs from REMOTE_ADDR 203.0.113.7 both returned 200. failed-jobs returns the first 1000 bytes of each exception message (SQLSTATE text, values, internal hostnames), plus job names, queues and Horizon ids. Each request can trigger up to 20 ZRANGEBYSCORE calls plus 10,000 HMGETs (with full payloads for failed jobs, see C13) and per-queue delayed scans, with no auth and no throttling. AllowIps uses `$request->ip()`, so it can be spoofed with X-Forwarded-For when TrustProxies is `*`. The routes are registered even when `prometheus.enabled` is false or the package is disabled. The README warns about all this, but the shipped default is open.
- **Recommendation:** Default to closed. Require an explicit auth mechanism (a bearer token checked with hash_equals, a Gate, or a configurable middleware list with no permissive default), and return 403/404 when nothing is configured. Add `throttle` middleware, register the routes only when the feature is enabled, and consider dropping or redacting exception messages unless explicitly opted in.

## C5 [medium] Collector failure isolation is incomplete: Horizon Redis outage makes /metrics 500

**Verifier verdict: confirmed.** HorizonWorkloadCollector:35 calls WorkloadRepository::get() outside ScrapeCache. Vendor RedisWorkloadRepository::get hits Redis (supervisors, readyNow). spatie's HorizonStatusCollector calls MasterSupervisorRepository::all() unguarded, and the provider docblock (provider:31-32) admits this. Either throws a RedisException out of the render and returns a 500. ProvisioningPlan.php:186 in vendor Horizon 5.50 does throw on minProcesses<1, but Horizon itself would not start then, so that sub-case is marginal. The Redis-outage path is the real one.

- **Location:** src/Prometheus/HorizonWorkloadCollector.php:35, src/Prometheus/HorizonWaitsCollector.php:36, src/HorizonPrometheusGrafanaServiceProvider.php:73
- **Detail:** Three metric sources run without the ScrapeCache guard: HorizonWorkloadCollector calls `WorkloadRepository::get()` directly, HorizonWaitsCollector calls `HorizonQueues::byConnection()` / `ProvisioningPlan::get()` (which throws on an invalid horizon config, e.g. minProcesses < 1), and the provider registers spatie's HorizonStatusCollector itself. Probe with the Redis port closed: `horizon_status` and `horizon_current_processes` threw `RedisException: Connection refused` and /prometheus returned 500. During a Redis incident, all of the application's other metrics (HTTP, DB, custom) vanish with it, which is exactly when they are needed.
- **Recommendation:** Route every source through one guarded reader (ScrapeCache with typed defaults). Replace spatie's HorizonStatusCollector with a guarded equivalent, or wrap it in a decorator. Add a test that renders /metrics with Redis down and with a broken horizon config.

## C6 [medium] Sync/deferred/background jobs are recorded and write to Redis from the web process

**Verifier verdict: confirmed.** Verified the vendor change. SyncQueue in v12.40.0 has no JobAttempted dispatch. v12.45.0 and the installed 12.70 call raiseJobAttemptedEvent in `finally` (SyncQueue.php:138-139). DeferredQueue and BackgroundQueue extend SyncQueue. handleJobProcessing skips SyncJob, but handleJobAttempted does not, so finish() runs recordAttempt with startedAt=null and still does HINCRBY jobs_total plus the pipeline round trip in the web or test process. The docblock assumption at subscriber:27-28 is outdated.

- **Location:** src/QueueJobMetricsSubscriber.php:27-28, src/QueueJobMetricsSubscriber.php:108-112, src/QueueJobMetricsSubscriber.php:134-137
- **Detail:** The docblock assumes SyncQueue never fires JobAttempted, and only handleJobProcessing skips SyncJob. Since roughly Laravel 12.4x, `SyncQueue::executeJob` dispatches JobAttempted in `finally` (vendor SyncQueue.php:139; absent in v12.40, present in v12.45). DeferredQueue and BackgroundQueue extend SyncQueue. Probe: `dispatch()` with `queue.default=sync`, plus `dispatch_sync()`, produced `queue_jobs_total{connection="sync",queue="sync",job_class="ProbeJob",status="completed"} 2`, zero-filled to 5 series. Each sync job now does a Redis pipeline inside the HTTP request or test. With an unreachable metrics Redis (blackholed host), one sync dispatch blocked for 60.05 s on the phpredis connect timeout. Test suites using QUEUE_CONNECTION=sync without Redis therefore get a Redis connection attempt plus a warning log per dispatched job.
- **Recommendation:** In handleJobAttempted and handleJobTimedOut, return early unless an attempt was registered in handleJobProcessing (`isset($this->attempts[$id])`), or skip `SyncJob` explicitly there too. Better: only record for connections whose driver is in a configurable allow-list (default `redis`). Add tests for sync, deferred and background.

## C7 [medium] Every app replica exports the same global counters, so sum() in the dashboard and alerts multiplies by the replica count

**Verifier verdict: confirmed.** All queue, job and batch series come from shared Redis or DB, so every scraped replica emits identical series. The dashboard and alert expressions use `sum by (queue, job_class, status)(office_queue_jobs_total…)` (verified in queues.json), which multiplies by N. This is a documented design limitation with a relabel workaround (README:8, 76-83), not a code bug, but it is reachable with standard k8s pod discovery and the per-scrape cost is multiplied too.

- **Location:** src/Prometheus/QueueJobsCollector.php:29-62, src/Prometheus/QueueStateCollector.php:24-70, resources/grafana/alerting/horizon.yml:124-126
- **Detail:** All queue, job and batch metrics are read from shared Redis or DB, so each app instance serving /metrics returns identical series that differ only by `instance`/`pod`. With Kubernetes pod discovery, PodMonitor, or several static targets, the dashboard expressions (`sum by (queue, job_class, status)(app_queue_jobs_total…)`) and similar queries report N times the real throughput and pending counts. The only mitigation is README line 8 ('scrape one instance'), and it conflicts with users' need to scrape app-level metrics from every pod. Each replica also runs the reader Lua and the batch SQL, multiplying the per-scrape cost (C12, C15).
- **Recommendation:** Serve the package metrics on a separate spatie urlName/endpoint, so a single Service target can scrape them while app metrics stay per-pod. Make the dashboard and alert queries replica-safe (`max without (instance, pod) (...)` before aggregating), or add an `exporter` label and document dedup. Optionally take a Redis lock per scrape window so only one replica computes the expensive sources.

## C8 [medium] queue_oldest_pending_job_age includes the dispatch delay and earlier attempts, causing false 'Queue wait over 2x limit' alerts

**Verifier verdict: confirmed.** The Lua script uses pushedAt/createdAt of the head job (RedisQueueStateReader.php:94). migrateExpiredJobs RPUSHes delayed or released payloads to the tail unchanged, so the head age of such a job includes the delay, the backoff and earlier runtimes. QueueState's docblock admits this. horizon.yml:90-91 compares it to the wait threshold with a >2 ratio for 5 minutes, so a debounce-heavy queue with a steady small backlog trips it. Correction to the claim: delay is in the Horizon payload only with Laravel ≥12.11 AND Horizon ≥5.49. Checked raw tags: v5.40 to v5.48 lack the version_compare. Retries are skewed on every version.

- **Location:** src/RedisQueueStateReader.php:38-39, src/RedisQueueStateReader.php:94, src/Prometheus/QueueStateCollector.php:61-68, resources/grafana/alerting/horizon.yml:90-91
- **Detail:** The head job's ready time is `pushedAt` (or `createdAt`), i.e. the dispatch time. Delayed jobs, released/backed-off retries and expired reserved jobs are migrated to the tail of the list with their original payload. Once such a job reaches the head, its 'age' is delay + earlier runtimes + actual wait. Example: a queue that receives `->delay(600)` debounce jobs and has a small steady backlog, with the default 60 s threshold. Every head job reports ≥ 600 s, the ratio is ≥ 10, and after 5 minutes `horizon-long-wait` fires although the real wait is seconds. The comment says the delay cannot be known because 'Horizon does not write it', but that is outdated. With Laravel ≥ 12.11, Horizon's later() passes `$delay` into createPayload, and the probe showed the payload `delay=30` next to pushedAt.
- **Recommendation:** In Lua, compute the head ready time as pushedAt + delay (both are top-level payload keys). For retried or released jobs (attempts > 0), either treat the age as unknown and fall back to firstDueAt or to Horizon's wait-time estimate, or record the actual release/migrate time. Correct the comments and the help text, and add tests with delayed, released and retried head jobs.

## C9 [medium] Unbounded label cardinality and no series expiry (job_class from displayName, batch kind/name/id labels)

**Verifier verdict: confirmed.** The job_class label is resolveName(), i.e. displayName (subscriber:161). CallQueuedClosure names closures 'Closure (file:line)', and a custom displayName() with IDs is user-controlled. The storage hashes never expire (storage docblock :28-31). jobsTotal zero-fills 5 statuses, giving about 25 series per class. BatchKind::of only strips UUIDs, digits and separator runs, so 'export-ab3f9e' becomes 'export-abfe' and e-mails survive unchanged. Per-batch series are bounded (200 per kind per day) but churn, and `status` is a label. The impact depends on user naming, but the code has no cardinality guard.

- **Location:** src/QueueJobMetricsSubscriber.php:158-165, src/QueueJobMetricsStorage.php:28-31, src/QueueJobMetricsStorage.php:228-247, src/BatchKind.php:15-20, src/Prometheus/QueueBatchesCollector.php:32, src/Prometheus/QueueBatchesCollector.php:102
- **Detail:** The `job_class` label is `resolveName()`, i.e. the payload displayName. That is user-controlled: a custom `displayName()` such as `"Import #{$id}"` creates a new series set per job, and closures are named `Closure (web.php:42)`, which changes with every edit that moves the line. Each distinct value creates about 25 series: 5 statuses (zero-filled by jobsTotal), 16 buckets, sum, count, min, max. They are stored in Redis hashes that never expire and are exported on every scrape forever, which the storage docblock confirms. BatchKind only strips digits, UUIDs and separators. Names containing hex hashes (`export-ab3f9e…` becomes `export-abfe…`), e-mails or customer names stay unique per batch, so the `batch` label grows without bound in queue_batches_running, queue_batch_jobs, queue_batch_info and batch_job_classes. Per-batch gauges add `name` and `id`, plus `size` and `created` labels, for up to 200 batches per kind. With many kinds this reaches tens of thousands of high-churn series, and Running→Finished status changes create new series too.
- **Recommendation:** Label by job class (`data.commandName` or the resolved class) instead of displayName, or make the label resolver configurable with a normalizer. Cap distinct values per family and fold the overflow into an `other` label. Track last-seen time per field and prune fields not seen for N days (for example a ZSET index per hash). Allow a user-defined BatchKind resolver, cap kinds globally, and drop `id`, `size` and `created` from labels (serve per-batch rows through the JSON endpoint instead).

## C10 [medium] Redis Cluster is not supported: phpredis cluster has no pipeline() and the Lua scripts touch cross-slot keys

**Verifier verdict: confirmed.** Local phpredis 5.3.7: method_exists('RedisCluster','pipeline') is false. Laravel RedisQueue::bulk special-cases PhpRedisClusterConnection (RedisQueue.php:186), and Horizon 5.50 has UsesClusterAwarePipeline for the same reason. recordAttempt, pullReadyAt and HorizonJobsRepository::scan all call pipeline(). EXTREMES_SCRIPT uses ':min'/':max' keys and RESET_SCRIPT uses meta plus 5 counters with no hash tag, so they hit different slots and fail with CROSSSLOT. Note that the Horizon docs still say cluster is unsupported, so this is a scope limitation for a public package rather than a regression.

- **Location:** src/QueueJobMetricsStorage.php:106, src/QueueJobMetricsStorage.php:120-126, src/QueueJobMetricsStorage.php:189-192, src/QueueJobMetricsStorage.php:212-217
- **Detail:** recordAttempt() and pullReadyAt() call `Connection::pipeline()`, which calls `$client->pipeline()`. `method_exists('RedisCluster','pipeline')` is false in phpredis 5.3.7, so every attempt throws (caught, with a warning logged per job), and Laravel's own RedisQueue::bulk special-cases clusters for this reason. Separately, EXTREMES_SCRIPT uses `…:<window>:min` and `…:max`, and RESET_SCRIPT uses meta plus 5 counter keys. All of them hash to different slots, so EVAL fails with CROSSSLOT. On a cluster deployment you get no job metrics and a log line per job. The README says nothing about cluster.
- **Recommendation:** Put a common hash tag in every storage key (e.g. `{hob}:jobs_total`), so the scripts and multi-key operations stay in one slot. On cluster connections, use `transaction()` or plain sequential commands instead of `pipeline()`. Otherwise detect cluster connections and fail fast with one clear log message. Document supported topologies.

## C11 [medium] Metrics Redis outage or slowness blocks every job and every delayed dispatch (no circuit breaker or timeouts) and floods logs

**Verifier verdict: confirmed.** RedisManager::connection caches a connection only after resolve() succeeds, so a failed connect is retried on every call. PhpRedisConnector passes timeout 0.0 by default, which means default_socket_timeout. The catch blocks swallow errors but not the latency, and each failure logs a warning. The scenario is narrow: with the default HPG_REDIS_CONNECTION=default the queue Redis is the same server, so an outage already stops workers. The per-job blocking matters when a separate metrics Redis is blackholed or slow, which the config explicitly supports. The log flood happens in any outage.

- **Location:** src/QueueJobMetricsSubscriber.php:97-105, src/QueueJobMetricsSubscriber.php:157-171, src/QueueJobMetricsSubscriber.php:241-251, src/QueueJobMetricsStorage.php:471-474
- **Detail:** The catch blocks only stop exceptions; the time spent before the failure is still paid. Each failed call re-resolves the connection (Laravel does not cache a failed connection), and phpredis connects with default_socket_timeout (60 s) unless the user set `timeout`. With `HPG_REDIS_CONNECTION` pointing at a separate Redis that becomes unreachable (blackholed host, security group, DNS to a dead IP), every job pays up to two connect timeouts: pullReadyAt in JobProcessing when the wait is ≥ 1 s, and recordAttempt. Every web request dispatching a delayed job or a batch job also pays one. The sync probe measured 60.05 s for a single dispatch. The 'metrics never affect job processing' goal is violated, and a `Log::warning` per job floods the logs at high throughput.
- **Recommendation:** Add a per-process circuit breaker: after a failure, skip metric writes for N seconds and log once per window. Recommend or enforce short `timeout`/`read_timeout` on the metrics connection. Avoid Redis reads in JobProcessing entirely (see C18).

## C12 [medium] Per-scrape Lua scan copies up to 2,000 full payloads per queue while Redis is blocked; reserved scan not configurable

**Verifier verdict: refuted.** The mechanics are right: up to pending_scan_limit LRANGE payloads plus up to 1000 reserved per queue, and RESERVED_SCAN_LIMIT is hard-coded. The severity rests on 200 KB payloads being 'often'. SerializesModels stores ModelIdentifiers, so model and collection payloads are small. :reserved is bounded by busy worker processes. The README's own measurement (20 KB × 1000 ≈ 40 ms per EVAL) puts even 10× larger payloads far below the 5 s BUSY threshold, and each queue is a separate EVAL. The cost is documented and tunable (HPG_PENDING_SCAN_LIMIT=0). Only the non-configurable reserved limit is a minor nit.

- **Location:** src/RedisQueueStateReader.php:30, src/RedisQueueStateReader.php:58-81, config/horizon-prometheus-grafana.php:32
- **Detail:** For each queue, every scrape (from every replica, see C7) runs LRANGE over up to `pending_scan_limit` (default 1000) full payloads in chunks of 500, plus ZRANGE over up to RESERVED_SCAN_LIMIT=1000 reserved payloads. The reserved limit is hard-coded and still applies when pending_scan_limit=0. All of this is materialized inside Lua with Redis single-threaded. Payloads with serialized models or collections are often 50–500 KB: at 200 KB, 500 payloads per LRANGE chunk means about 100 MB of Lua strings at once, and 2,000 per queue means about 400 MB copied per queue per scrape. Past busy-reply-threshold (5 s by default), every other client, including Horizon workers and the app's cache and sessions, gets BUSY errors, and Lua memory can spike Redis toward maxmemory. With 10 queues, 3 replicas and a 15 s interval, the load is continuous.
- **Recommendation:** Make the reserved scan limit configurable (default much lower, e.g. 100) and cap the total bytes scanned. Use `LRANGE` with smaller chunks and stop early once the head is known. Consider sampling with a small limit and extrapolating. Cache the per-class breakdown for N seconds across replicas (with a Redis lock) instead of recomputing it on every scrape.

## C13 [medium] JSON endpoints scan up to 10,000 rows with full payloads, even when the filter cannot match anything

**Verifier verdict: confirmed.** (2) holds. supervisorQueues returns [] for a non-running supervisor, intersect gives [], and array_flip([]) gives [], which is not null, so every row is rejected while the loop still runs to SCAN_LIMIT: 20 ZRANGEBYSCORE + 10k HMGETs, and for failed jobs FAILED_FIELDS pulls full payloads only to read `attempts`. The DelayedJobsRepository sub-claim is mostly unreachable: when the batch or supervisor filter empties, getDelayed's array_intersect empties the queue list first. The 300 MB OOM figure assumes atypical 200 KB payloads and is overstated.

- **Location:** src/Repositories/HorizonJobsRepository.php:25, src/Repositories/HorizonJobsRepository.php:140-183, src/HorizonJobs/HorizonJobsService.php:85-93, src/HorizonJobs/HorizonJobsService.php:132-135, src/Repositories/DelayedJobsRepository.php:35, src/Repositories/DelayedJobsRepository.php:66-99
- **Detail:** (1) FAILED_FIELDS includes `payload`, so for failed-jobs every scanned row, including rows rejected by the queue or class filter, brings its full payload into PHP: 500 per chunk and up to 10,000 per request. Matching rows keep the payload in `$result` until map(), up to limit=1000. With 200 KB payloads that is roughly 1000×200 KB + 500×200 KB ≈ 300 MB, which exceeds a typical 128–256 MB memory_limit and produces a 500. (2) When a filter resolves to an empty list, `intersect()` returns [] and `array_flip([])` is [], so every row is skipped but the loop still runs to SCAN_LIMIT (20 round trips, 10,000 HMGETs). This happens when the selected supervisor is not running (exactly during incidents), when a batch kind has no links, or with C14. DelayedJobsRepository behaves the same way per queue (`$jobs=[]`), JSON-decoding up to 10,000 full delayed payloads per queue.
- **Recommendation:** Return an empty result immediately when the queue or job filter is an empty array. Filter on light fields first (id, name, queue, time) and fetch `attempts` only for the final page, either with a small Lua script that extracts the number or from the hash field Horizon keeps. Cap total bytes per request. For delayed jobs, extract displayName/uuid/attempts in Lua instead of returning whole payloads.

## C14 [medium] Supervisor filter matches nothing for supervisors with balance=false/off (multi-queue single pool)

**Verifier verdict: confirmed.** In vendor Horizon 5.50, Supervisor::createProcessPools uses a single pool when balancing() is false (balance not simple/auto). RedisSupervisorRepository::update keys processes as `connection:` + $pool->queue(), which gives 'redis:default,slow'. supervisorQueues (HorizonJobsService:232-233) yields 'default,slow', which never equals a job hash's single `queue` field, so all three tables come back empty and trigger the full scan from C13. Splitting on ',' would fix it.

- **Location:** src/HorizonJobs/HorizonJobsService.php:143-159

## C15 [medium] Batch collector loads every never-finished batch on every scrape (unbounded SQL scan)

**Verifier verdict: confirmed.** With allowFailures, a failed job increments failed_jobs without decrementing pending_jobs, so pending never reaches 0 and finished_at is never set. The collector's docblock (:22-25) acknowledges this. queue:prune-batches only deletes these rows with --unfinished. The default job_batches migration only has a primary key, so the OR filter on finished_at/cancelled_at is a full table scan. Lost-job batches stay 'Running' forever. - **Location:** src/Prometheus/QueueBatchesCollector.php:233-248
- **Detail:** The query is `WHERE (finished_at IS NULL AND cancelled_at IS NULL) OR finished_at >= ? OR cancelled_at >= ?`. ## C19 [low] Wait histogram records 0 for retried (horizon:retry / queue:retry) jobs that were originally delayed

## C21 [low] Counter reset logic wipes data on first scrape, on meta-key loss, and on harmless failovers

**Verifier verdict: refuted.** The predis-replication premise is wrong.
