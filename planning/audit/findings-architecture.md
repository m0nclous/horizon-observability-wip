# Design findings (A01-A28)

Audit of the legacy pilot (now in `legacy/`), 2026-10-16. File:line references point to the legacy layout (`src/...` = `legacy/src/...`).

## Summary

The PHP code is a carefully reasoned pilot, but it is shaped for one app ("office"). Most logic sits in a few large classes with hidden global contracts. The audit found 4 high-severity issues, all checked against upstream sources.

1. **Dispatch crash:** a `JobQueued` listener casts `$event->delay` with `(int)` outside its try/catch. Any `->delay(now()->addMinutes(5))`, `Mail::later(...)` or delayed notification makes Laravel throw an `ErrorException` at the dispatch call site in the host app.
2. **Sync jobs pollute metrics:** since a later Laravel 12.x, `SyncQueue`, `DeferredQueue` and `BackgroundQueue` also fire `JobAttempted`. The subscriber skips `SyncJob` only on `JobProcessing`, so every sync job is written to Redis as `connection="sync"`. The dashboard sums by queue, so these attempts inflate the real queue's numbers.
3. **`/metrics` can return 500:** the provider promises collectors never break `/metrics`, but `QueueBatchesCollector` reads `stats()['kinds']` after the failure fallback has returned `[]`. A missing `job_batches` table or DynamoDB batching therefore turns `/metrics` into a 500. The workload, waits and spatie `horizon_status` collectors have no guard at all.
4. **spatie/laravel-prometheus coupling:** the package relies on an unchecked global setting (`prometheus.cache = null`) and fakes histograms as three counter families. Its metric names collide with spatie's own collectors in the same registry. spatie 1.5+ requires PHP 8.4, so on PHP 8.3 the package is limited to spatie 1.3–1.4 and cannot run on Laravel 13.

Medium issues:
- Laravel 13 removed `JobAttempted::$exceptionOccurred`.
- The provider mutates `horizon.middleware` from `register()`. After the rename to `df/...`, the package's provider registers before Horizon's. If `config/horizon.php` is not published, this drops Horizon's `web` middleware.
- `QueueJobMetricsStorage` is a 475-line class with several jobs. Its pipelined `eval` call uses the phpredis argument order, so it fails under predis.
- The extra Redis key that records when a delayed job becomes ready is redundant: Laravel ≥12.11 with Horizon ≥5.49 already writes `delay` into the payload.
- Job-class discovery only scans `app/`, misses inherited `ShouldQueue`, and its static cache does nothing under PHP-FPM.
- `HorizonWorkloadCollector` calls the expensive `WorkloadRepository::get()` but uses only `processes`.
- The batches query fetches every never-finished batch on every scrape, without limit.
- The HTTP layer has dead code and pulls in spatie/laravel-data for one DTO.
- Static state, service location and `time()` make the code hard to test.
- The config shape is misleading, and office leftovers remain in code, help text and label values.

Dependency verdicts:
- **spatie/laravel-prometheus:** replace with promphp's `MetricFamilySamples` / `RenderTextFormat` plus the package's own endpoint, with an optional spatie bridge.
- **spatie/laravel-data:** drop it.
- **spatie/laravel-package-tools:** adopt it.


## A01 [high] (int) cast of JobQueued::$delay throws in the host app for DateTimeInterface/DateInterval delays

- **Location:** src/QueueJobMetricsSubscriber.php:90 (outside the try at :97)
- **Detail:** `$delay = (int) $event->delay;` runs before the try/catch and before the driver check, so it runs for every connection. Illuminate RedisQueue::later and Horizon's RedisQueue::later (5.50) pass the raw delay to JobQueued. That delay is often a Carbon/DateInterval: `->delay(now()->addMinutes(5))`, `Mail::later(now()->addMinute(), ...)`, delayed notifications. PHP emits 'Object of class ... could not be converted to int' (verified). Laravel's HandleExceptions::handleError (error_reporting(-1)) turns it into an ErrorException. That exception propagates out of the event listener into the dispatch call site. The job is already pushed, but the caller crashes, which can roll back the surrounding transaction and leave the job orphaned.
- **Recommendation:** Normalize the delay with a helper that mirrors InteractsWithTime::secondsUntil (int, DateTimeInterface or DateInterval to seconds) and run it inside the guarded block. Better: with Laravel >= 12.11 and Horizon >= 5.49 the payload already carries `delay` in seconds (see A08), so the delay branch can be deleted. Add a regression test that dispatches with a Carbon delay.

## A02 [high] Sync/deferred/background queue attempts are recorded (SyncQueue now fires JobAttempted)

- **Location:** src/QueueJobMetricsSubscriber.php:108-118 vs :134-137, :149-173; class docblock :27-28
- **Detail:** The docblock assumes SyncQueue fires JobProcessing but not JobAttempted. That holds for illuminate/queue 12.0.0 only. In 12.70 and 13.x, SyncQueue::executeJob calls raiseJobAttemptedEvent in `finally`, and DeferredQueue/BackgroundQueue extend SyncQueue. handleJobProcessing skips SyncJob, but handleJobAttempted does not. Result: every dispatch_sync, `QUEUE_CONNECTION=sync` job and deferred job does a Redis pipeline write in web requests. It also creates `queue_jobs_total{connection="sync",queue="default"}` series. The dashboard aggregates `sum by (queue)` almost everywhere, so sync attempts are added to the real `default` queue's Completed/Failed/Success rate. Attempts are also recorded for database/sqs connections that Horizon does not run.
- **Recommendation:** Filter at a single entry point on every handler: skip `SyncJob` and record only connections in an allowlist. The default allowlist is the connections that HorizonTopology reports for the current environment; config `attempts.connections` can override it. Cover with tests for sync, deferred and redis connections on Laravel 12.0, 12.x and 13.

## A03 [high] Failure isolation is ad hoc: several paths still turn a source failure into a /metrics 500

- **Location:** src/Prometheus/QueueBatchesCollector.php:178,198 with src/Prometheus/ScrapeCache.php:42; src/Prometheus/HorizonWorkloadCollector.php:35; src/Prometheus/HorizonWaitsCollector.php:36; src/HorizonPrometheusGrafanaServiceProvider.php:26-33,73
- **Detail:** ScrapeCache::remember returns `[]` on any failure. QueueBatchesCollector then does `foreach ($this->stats()['kinds'] ...)` and `['batches']`. On `[]` that is 'Undefined array key' plus a foreach-on-null warning, which Laravel's error handler converts to ErrorException (verified). So a missing job_batches table, wrong `queue.batching.database`, or the DynamoDB batching driver makes the whole /metrics endpoint return 500 on every scrape, including the host app's own metrics. A missing table is the default in a fresh project without the batches migration. HorizonWorkloadCollector (WorkloadRepository::get, Redis) and HorizonWaitsCollector (ProvisioningPlan::convert throws on minProcesses < 1) have no guard. spatie's HorizonStatusCollector, registered at provider:73, has none either. The provider docblock acknowledges the spatie one, but its claim that package collectors never break /metrics is false.
- **Recommendation:** Move isolation out of the collectors into the exporter. Each collector runs in its own try/catch; on failure its families are dropped, the error is reported through a throttled reporter, and `<ns>_collector_success{collector}` / `<ns>_collector_duration_seconds{collector}` are emitted (node_exporter style). Ship the package's own `horizon_status` collector with the same name and values so spatie's unguarded one is not needed. Type the memo per source (or give `remember()` an explicit default) so a fallback can never change shape. Add tests that make each source throw and assert a 200 response.

## A04 [high] spatie/laravel-prometheus coupling: hidden global contract, fake histograms, PHP 8.4 floor, name collisions

- **Location:** composer.json:12; src/Prometheus/QueueJobsCollector.php:35,72-93; src/HorizonPrometheusGrafanaServiceProvider.php:72-86; config/horizon-prometheus-grafana.php:3-10
- **Detail:** (1) Counters publish absolute Redis values through `Counter::inc()`. This is only correct with `prometheus.cache = null` and an in-memory registry. Nothing checks it. A host that uses spatie's cache adapter for its own per-request counters (the main reason to use the adapter) gets this package's counters inflated on every scrape. (2) spatie has no way to export pre-aggregated histograms. `_bucket`/`_sum`/`_count` are emitted as three `# TYPE ... counter` families, so metadata is wrong and promtool lint flags them. (3) spatie 1.5.0 to 1.7.1 require `php ^8.4` (verified). On PHP 8.3 composer can only pick 1.3/1.4, which support Laravel 11/12 only, so PHP 8.3 + Laravel 13 is not installable. (4) Collectors share spatie's singleton registry and namespace. spatie's own collectors, which its README and published stub encourage registering, use the same names: `queue_pending_jobs`, `queue_delayed_jobs`, `queue_oldest_pending_job_age` (connection, queue), `horizon_current_processes` (queue), `horizon_status`. getOrRegisterGauge returns the same gauge, the last writer silently wins, and semantics differ (spatie's pending excludes due-delayed jobs). (5) Package metrics are cluster-global (read from shared Redis). Mixing them into the per-instance app /metrics forces 'scrape exactly one instance' on the app's own metrics too. (6) All collectors are resolved and registered on every app boot, including web requests and Horizon workers.
- **Recommendation:** Depend on promphp/prometheus_client_php (php ^8.2, no Laravel constraint) only for MetricFamilySamples + RenderTextFormat, which renders real histogram families with identical series names. The dashboard queries stay unchanged. Ship the package's own endpoint at `<http.prefix>` (default `metrics/horizon`), with its own registry and a configurable namespace. Collectors are resolved lazily inside the controller. For users who want a single /metrics, offer an opt-in bridge (`suggest: spatie/laravel-prometheus`): a subclass of spatie's `RenderCollectorsAction` (its supported `actions.render_collectors` extension point) that appends the package's rendered families. Have `horizon-observability:check` / AboutCommand flag a non-null `prometheus.cache` when the bridge is on.

## A05 [medium] Laravel 13 incompatibility in attempt status resolution; JobTimedOut::$timeout unused

- **Location:** src/QueueJobMetricsSubscriber.php:181, :195-201
- **Detail:** Laravel 13's JobAttempted is `__construct($connectionName, $job, $exception = null)`: `$exceptionOccurred` no longer exists (verified in illuminate/queue 13.37). `$job->isReleased() && $event->exceptionOccurred` is evaluated for every released job. On Laravel 13 that is an 'Undefined property' warning, which becomes an ErrorException. It is thrown from resolveStatus() before finish()'s try, so the exception escapes the listener into Worker::process's finally block and gets reported for every retry/release, and the attempt is lost. Laravel 13's JobTimedOut also carries `$timeout`, which closes the gap described at :188-192 (supervisor `--timeout` is not visible via `$job->timeout()`).
- **Recommendation:** Use `$event->exception !== null` when the property exists, else `$event->exceptionOccurred`, isolated in a small `AttemptOutcome::fromEvent()` mapper with tests on 12.0, 12.x and 13.x. Prefer `$event->timeout ?? $job->timeout()` for the timeout cap. Plan composer `laravel/framework: ^12.11|^13.0` with a CI matrix.

## A06 [medium] Mutating horizon.middleware from register() is order-dependent and becomes harmful after the rename

- **Location:** src/HorizonPrometheusGrafanaServiceProvider.php:48; src/Http/Middleware/AddGrafanaLinkToHorizon.php:19-48
- **Detail:** `config()->push('horizon.middleware', ...)` assumes Horizon's config is already present. Package discovery registers providers in installed.json order, which is alphabetical by package name. `sushi-market/...` sorts after `laravel/horizon`, but `df/horizon-observability` sorts before it. Then, if the app has not published config/horizon.php, push() creates `horizon.middleware = [AddGrafanaLinkToHorizon]`. Horizon's later mergeConfigFrom keeps the app value, which drops the default `['web']`: no session, the gate fails outside local. A string `'middleware' => 'web'` makes push() fatal. The middleware is registered even when `grafana_url` is empty, and then runs on every Horizon request. Horizon >= 5.45 (verified, absent in 5.40) builds a dedicated `horizon` middleware group in boot().
- **Recommendation:** Do not touch Horizon's config. When `horizon_menu.grafana_url` is set and Horizon is installed, call `$this->app->booted(fn () => Route::pushMiddlewareToGroup('horizon', InjectGrafanaMenuLink::class))`. Require laravel/horizon ^5.49 (also needed for A08). Keep the HTML-marker approach, but put the marker strings in one place and add a test against the real Horizon layout view so a markup change fails CI instead of silently removing the link.

## A07 [medium] QueueJobMetricsStorage is a god class with driver-specific Redis calls and per-attempt overhead

- **Location:** src/QueueJobMetricsStorage.php:33-475 (pipeline eval :120-126; bounds() :104,:416-422; keys :35-41)
- **Detail:** One class handles counters, histogram encoding and cumulative math, minute-window extremes, the delayed ready-at side channel, the batch-job-class index, run_id reset, the JSON label codec and Redis connection resolution. Inside `pipeline(fn ($pipe))` the raw client is used: `$pipe->eval($script, [keys+args], 2)` is the phpredis signature. predis expects `eval($script, $numkeys, ...$args)`, so under predis min/max are never written and every attempt logs a warning (A17). The connection-level `eval` calls at :212 and in the readers are portable, because Laravel normalizes them. bounds() reads config, maps and sorts on every job attempt. Keys use the generic `prometheus:queue:` prefix with no hash tag and no schema version. Multi-key Lua (2 keys at :120, 6 keys at :212) gives CROSSSLOT on Redis Cluster.
- **Recommendation:** Split into AttemptStore (contract), RedisAttemptStore (write and read), HistogramSnapshot (pure cumulative math, unit-tested), LabelCodec, CounterResetGuard and BatchJobClassIndex. Write each attempt with ONE Lua script through the connection-level eval: HINCRBY total, bucket and sum plus min/max plus EXPIRE in a single round trip, atomic, client-agnostic. Alternatively, with Redis >= 6.2, use `ZADD LT/GT` sorted sets for the extremes and drop Lua from the hot path. Precompute validated buckets once in a typed config object. Keys become `{horizon-observability}:v1:...` (hash tag plus schema version); document the counter reset on migration from `prometheus:queue:*`. Load Lua from resources/lua/*.lua through a LuaScript value object (sha1, EVALSHA with NOSCRIPT fallback).

## A08 [medium] Ready-at side channel is redundant on current Laravel/Horizon

- **Location:** src/QueueJobMetricsSubscriber.php:86-106, :226-228, :233-252; src/QueueJobMetricsStorage.php:139-147, :185-195
- **Detail:** For every delayed Redis dispatch the subscriber SETs `ready_at:<id>`. For every first attempt that waited >= 1 s, a worker pays a GET+DEL round trip. Since Laravel 12.11, Queue::createPayload writes `delay` (seconds) into the payload. Horizon's RedisQueue::later passes the delay into the payload only from 5.49.0 (verified absent in 5.31 to 5.48). With Horizon < 5.49 on Laravel >= 12.11 the key exists but is null, so `array_key_exists('delay')` is not a reliable detector. waitSeconds() already adds `$payload['delay']`.
- **Recommendation:** Raise the floors to laravel/framework ^12.11 and laravel/horizon ^5.49, then delete rememberReadyAt/pullReadyAt, the delay branch of handleJobQueued and readyAt(). This also removes the A01 crash path. If older floors must stay, keep the store behind a `LegacyReadyAtStore` enabled only when the installed versions are older, decided once at boot.

## A09 [medium] Job-class discovery is app/-only, misses inherited ShouldQueue, and is not cached under PHP-FPM

- **Location:** src/QueuedJobClasses.php:27, :40-56 (:43 Finder, :46 getNamespace), :58-73
- **Detail:** Only `app_path()` is scanned, so jobs in modules, packages or `src/` layouts are invisible (docs/extraction.md item 3). `app()->getNamespace()` throws 'Unable to detect application namespace' when composer.json has no PSR-4 entry for app_path, as in testbench or modular apps. `->contains('ShouldQueue')` skips classes that inherit ShouldQueue from a base class. class_exists() autoloads every candidate during a scrape. The static cache (:27) only lasts per PHP process: under FPM it is reset every request, so the ~100 ms scan (per the docblock) plus autoloading runs on every scrape. There is no way to supply or override the list.
- **Recommendation:** Introduce a `Contracts\JobClassDiscoverer` with a default FilesystemJobClassDiscoverer. Paths come from config (`job_classes.paths`, default [app_path()]); namespaces are resolved from composer's PSR-4 map rather than getNamespace(), and an `extra` list is appended. Use reflection-based `implementsInterface(ShouldQueue::class)` after a cheap prefilter. Persist the result to bootstrap/cache via `horizon-observability:cache` / `:clear` registered with `$this->optimizes(...)` (available in Laravel 12.0.0, verified), so `php artisan optimize` warms it. Fall back to a runtime scan memoized in the Laravel cache with a deploy-hash key.

## A10 [medium] Per-scrape memo via scoped container binding and service location

- **Location:** src/HorizonPrometheusGrafanaServiceProvider.php:44; src/Prometheus/ScrapeCache.php:19-45; app(ScrapeCache::class) in QueueJobsCollector.php:102, QueueStateCollector.php:115, QueueBatchesCollector.php:162,228, HorizonSupervisorsCollector.php:106, QueueJobClassesCollector.php:23
- **Detail:** spatie keeps collector instances (and their closures) for the whole process. The code therefore cannot constructor-inject per-scrape state and resolves a scoped ScrapeCache from inside closures. ScrapeCache is also used for side-effect ordering (`':redis_restart'` returns [] at QueueJobsCollector.php:105-111). HorizonQueues::byConnection() is computed twice per scrape (RedisQueueStateReader.php:125, HorizonWaitsCollector.php:36). The design is correct but implicit and fragile, and it is the main reason collectors call `app()` instead of using DI.
- **Recommendation:** With the package's own exporter, pass an explicit `ScrapeContext` (memo, now, reporter) to `Collector::collect(ScrapeContext $ctx): iterable<MetricFamily>`. Collectors become stateless `final readonly` services with constructor DI. Pre-scrape hooks such as CounterResetGuard become explicit steps in Exporter. Remove the scoped binding.

## A11 [medium] HorizonWorkloadCollector pays for Horizon's full workload computation to read one field

- **Location:** src/Prometheus/HorizonWorkloadCollector.php:17-37 (:35)
- **Detail:** RedisWorkloadRepository::get() calls SupervisorRepository::all() twice: once for processes and once inside WaitTimeCalculator::calculate. It also calls readyNow() per queue and computes time-to-clear from Horizon metrics for every queue. The collector discards everything except `processes`. HorizonSupervisorsCollector already loads SupervisorRepository::all(), whose `processes` map is keyed exactly like the workload (`connection:queue`, including `a,b,c` for balance=false). It is also unguarded (A03).
- **Recommendation:** Build one `SupervisorSnapshot` list per scrape and derive `horizon_current_processes{queue}` by summing processes by `Str::after($key, ':')`. Same labels and values, one Horizon read instead of three, and a consistent snapshot. Merge both into HorizonSupervisorsCollector, or keep two collectors that share the snapshot through ScrapeContext.

## A12 [medium] QueueBatchesCollector: driver-unaware raw DB query, unbounded 'running' set, untyped arrays

- **Location:** src/Prometheus/QueueBatchesCollector.php:31-32, :174-219, :226-270 (query :233-242), :275-301 (status :281-285, created_label :297)
- **Detail:** It queries `queue.batching.table` directly and ignores `queue.batching.driver` (dynamodb is supported by Laravel). The where clause loads every row with NULL finished_at and cancelled_at on every scrape. allowFailures batches with failures never get finished_at, and `queue:prune-batches` without `--unfinished` never deletes them (the docblock acknowledges this), so the row set grows forever and is scanned without an index. Stats are `array<string,int|string|null>` bags. perKind/perBatch/row take callbacks returning either an int or a list, which is opaque. Status strings Running/Finished/Failures/Cancelled are a dashboard contract held as literals. The `created` label uses app.timezone, while README says UTC. CLOSED_WINDOW_SECONDS/RECENT_PER_KIND are not configurable.
- **Recommendation:** Move the logic to `Batches\BatchStatsReader` (database driver: bounded query adding `created_at >= now - batches.running_max_age` and/or `whereColumn('pending_jobs', '>', 'failed_jobs')` for the running branch; other drivers: skip with a collector_success=0 reason, or use BatchRepository::get with a cap). Return readonly `BatchSnapshot` / `BatchKindSummary` objects and a backed enum `BatchStatus` whose values are the dashboard strings. Make the windows, per-kind limit and label timezone configurable (default UTC to match docs). Keep the collector a thin mapper.

## A13 [medium] spatie/laravel-data used for one DTO, with a no-op mapper

- **Location:** composer.json:11; src/DTO/GetHorizonJobsDTO.php:7-34; src/Http/Requests/GetHorizonJobsRequest.php:57-60
- **Detail:** The only use is `GetHorizonJobsDTO extends Data` with `#[MapInputName(SnakeCaseMapper::class)]`. Every property name (supervisors, batches, queues, jobs, from, to, limit) is a single word, so the mapper does nothing. The FormRequest has already validated and normalized input. laravel-data pulls phpdocumentor/* and spatie/php-structure-discoverer, and forcing `^4.0` on hosts creates version conflicts for apps on other majors.
- **Recommendation:** Drop the dependency. Replace it with `final readonly class JobListQuery` (promoted ctor, `?list<string>` filters, `?CarbonImmutable` from/to, int limit) built by `JobListRequest::toQuery()`. Pass the object itself to the services and stores instead of spreading an associative array (HorizonJobsService.php:36,44,52,64).

## A14 [medium] HTTP response layer: dead base resource, duplicated formatting, DI inconsistency

- **Location:** src/Http/Resources/JsonResource.php:15-22; src/Http/Resources/Horizon*JobResource.php; src/Http/Controllers/HorizonJobsController.php:21-41; src/Repositories/HorizonJobsRepository.php:139,198; src/Repositories/DelayedJobsRepository.php:39
- **Detail:** All four endpoints return `XResource::collection(...)`, an AnonymousResourceCollection. ResourceResponse calls jsonOptions()/withResponse() on the collection, not on the item class (verified in illuminate/http 12). So `withResponse()` (JSON_UNESCAPED_*) never runs, and `public static $wrap = null` is a redeclared static that does not affect the collection. The base class is dead code. The ms conversion `(int) round($x * 1000)` is repeated 6 times across four near-identical resources. The controller extends Illuminate\Routing\Controller for no reason. Repositories use the Redis/Queue facades while RedisQueueStateReader injects QueueFactory. The response contract the dashboard relies on is: `{data:[...]}` plus fields name, queue, horizon_path, queued_at, completed_at, failed_at, available_at, attempts, runtime and exception.
- **Recommendation:** Replace resources with readonly row DTOs (`PendingJob`, `CompletedJob`, `FailedJob`, `DelayedJob`) implementing JsonSerializable with one shared ms helper. Return `response()->json(['data' => $rows], options: JSON_UNESCAPED_SLASHES|JSON_UNESCAPED_UNICODE)`. Use one invokable `JobListController` on `{list}-jobs` with implicit backed-enum binding (`JobListType`), and inject `Illuminate\Contracts\Redis\Factory` / `Queue\Factory` everywhere. Freeze the JSON shape with snapshot tests.

## A15 [medium] Route registration: ForceJsonResponse runs after access middleware; unnamed, always-on, insecure-by-default routes

- **Location:** src/HorizonPrometheusGrafanaServiceProvider.php:92-102 (:94); src/Http/Middleware/ForceJsonResponse.php:14-21; config/horizon-prometheus-grafana.php:38-41
- **Detail:** `[...config middleware, ForceJsonResponse::class]` puts AllowIps first. Its abort(403) is rendered before the Accept header is forced, so access errors come back as HTML, contrary to the middleware's docblock. Routes have no names, no enable switch and no throttle, and they are registered with `Route::` directly instead of `loadRoutesFrom`, so they are rebuilt even when routes are cached. The default access control is spatie's AllowIps, which allows everyone when `prometheus.allowed_ips` is empty. The job lists expose class names and exception messages, and can trigger up to 10k HMGETs per request (HorizonJobsRepository.php:29).
- **Recommendation:** Use routes/http.php loaded via loadRoutesFrom when `http.enabled`, named `horizon-observability.metrics` / `horizon-observability.jobs`. Middleware order: `[ForceJson::class, ...config('http.middleware')]`. Ship the package's own `AuthorizeScrape` middleware: a bearer token (`#[\SensitiveParameter]`, works with Prometheus `authorization` and an Infinity custom header) and/or an IP allowlist, failing closed in production when neither is configured. Add an optional `throttle:` entry. Keep the default prefix `metrics/horizon`: the dashboard's Infinity URLs hard-code it.

## A16 [medium] Config shape: misleading keys, legacy env prefix, hard-coded tunables, office leftovers, no validation

- **Location:** config/horizon-prometheus-grafana.php:19-52; constants in QueueJobMetricsStorage.php:57-64, QueueJobMetricsSubscriber.php:36-38, RedisQueueStateReader.php:30, QueueBatchesCollector.php:31-32, HorizonJobsRepository.php:26-43, DelayedJobsRepository.php:19-22
- **Detail:** `enabled` only toggles attempt metrics, not the package. The `HPG_` env prefix and the config/view namespace `horizon-prometheus-grafana` are hard-coded in 8 places (e.g. QueueJobMetricsStorage.php:418,473; AddGrafanaLinkToHorizon.php:27,43). Related settings are mixed in one flat list (storage, scan limits, HTTP, Horizon menu, dashboard TTS). Many operational knobs are private constants: extremes window, batch link TTL/refresh/memo, reserved scan limit, batch windows, list scan limits/chunks, exception byte cap. The comments are Russian and office-specific (`GRAFANA_PORT` at :46). Nothing validates buckets (sorted, positive), limits (>= 0) or the connection name; bounds() re-sorts on every attempt.
- **Recommendation:** Rename to config/horizon-observability.php with env prefix `HORIZON_OBSERVABILITY_`, grouped keys (see notes) and English comments. Read it through one `final readonly class ObservabilityConfig` built and validated once (singleton) and injected everywhere; no `config('...')` string calls in src/. Expose the tunables listed above. Report the effective config via `AboutCommand::add('Horizon Observability', ...)`.

## A17 [medium] Logging loses stack traces, floods from worker hot paths, and uses legacy Russian messages

- **Location:** src/QueueJobMetricsSubscriber.php:101,168,245,285; src/Prometheus/ScrapeCache.php:37; src/RedisQueueStateReader.php:142; src/Prometheus/QueueJobsCollector.php:107
- **Detail:** Every failure logs `Log::warning('QueueMetrics: <Russian text>', ['exception' => $e->getMessage()])` on the default channel. The exception object is dropped (no trace, no class), and nothing is throttled. If the metrics Redis is down, every job attempt in every worker logs a warning, and with predis every attempt does (A07). Workers can also block on the shared Redis connection's timeouts. There is no metric that exposes collector or recorder health.
- **Recommendation:** Add a `Support\FailureReporter`: configurable channel (`log_channel`), passes `'exception' => $e`, throttles per key per process (e.g. once per 60 s, with a suppressed count), and uses English messages with a stable `horizon-observability:` prefix. Expose `<ns>_collector_success{collector}` and `<ns>_attempt_write_failures` (or similar). Document a dedicated Redis connection with short connect and read timeouts for `storage.redis_connection`.

## A18 [medium] Load-test command and job ship in src/ with office-specific scenarios

- **Location:** src/Console/QueueLoadTestCommand.php:31-124,136,148; src/Jobs/QueueLoadTestJob.php:36-40,94-97; src/HorizonPrometheusGrafanaServiceProvider.php:65-67
- **Detail:** The QA-only tooling (docs/cleanup.md marks it for deletion) is autoloaded and registered in every console process, including production, where it is guarded only at runtime. Its queues (`default`/`slow`/`slow_reports`), task names and output are office-specific Russian. Outcomes are string constants, scenarios are positional tuples, and it uses mt_rand and usleep. The anonymous ShouldntReport exception is why HorizonJobsService::exceptionSummary needs the `@anonymous` regex (HorizonJobsService.php:116-121).
- **Recommendation:** Move it to `workbench/app/Console/Commands/SimulateLoadCommand.php` + `workbench/app/Jobs/SimulatedJob.php` (autoload-dev) for screenshots, demos and integration tests.
